# Download registry на ConcurrentHashMap

## Задача

Несколько worker-потоков загружают файлы. Им нужен общий реестр, чтобы:

- быстро найти загрузку по `id`;
- зарегистрировать разные загрузки параллельно;
- не запустить одну загрузку дважды, если два потока одновременно получили один `id`;
- не хранить элементы отсортированными;
- не ждать появления элемента, как в очереди.

## Карта решений

| Вариант | Почему подходит или не подходит |
|---|---|
| `HashMap` | конкурентное изменение не имеет безопасного контракта |
| `Collections.synchronizedMap` | корректна для отдельных вызовов, но использует один общий mutex; составное действие требует внешней синхронизации |
| `ConcurrentSkipListMap` | потокобезопасна, но оплачивает сортировку, которая реестру не нужна |
| `CopyOnWriteArrayList` | оптимизирована для частых обходов и редких записей, а не для поиска по ключу |
| `BlockingQueue` | передаёт элементы между producer и consumer, но не является реестром по ключу |
| `ConcurrentHashMap` | даёт конкурентный поиск по ключу и атомарные составные операции для одного ключа |

## Почему выбран ConcurrentHashMap

Требования совпадают с её контрактом:

```text
нужен поиск по id             → Map
с коллекцией работают потоки  → concurrent implementation
сортировка не нужна           → hash map, а не skip list
регистрация должна быть одна  → computeIfAbsent
```

Метод `findOrStart()` использует `computeIfAbsent()`. Вычисление нового значения для ключа
выполняется атомарно: конкурентный поток не может вклиниться между проверкой отсутствия ключа
и его добавлением.

## Запуск тестов

Из корня репозитория:

```bash
mvn test
```

Тест одновременно отправляет 32 запроса одного `id` и проверяет, что функция запуска
загрузки была вызвана ровно один раз, а все потоки получили один экземпляр `Download`.
